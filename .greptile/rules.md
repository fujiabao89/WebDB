# WebDB Greptile 代码审查规则

## 0. 定位与可信边界

Greptile 用于发现和解释代码问题，不是 WebDB 的最终合并门禁。Greptile 原生评论、置信度和 GitHub 状态不得替代可信 CI、Task 验收矩阵或独立 Reviewer 的最终结论。

仓库内 `.greptile/` 配置可被更具体的子目录配置覆盖，因此本文件不是不可绕过的安全边界。SQL、权限、凭证、审计和数据隔离等关键规则还必须由仓库 Owner 在 Greptile 组织级配置为 enforced，并使用 CODEOWNERS 或可信 CI 保护根目录及任意嵌套 `.greptile/**` 的变更。

## 1. 权威来源与审查前提

按以下优先级解决冲突：用户当前指令 > 根 `AGENTS.md` > 目录级 `AGENTS.md` > 已接受 ADR > `webdb-design-draft.md` > 代码注释。提议、草案、待批准或拟替代 ADR 在正式接受前不得覆盖已接受 ADR。

开始审查前必须读取并核对：

1. PR 标题/正文中的 Task 或 Issue ID，并用它定位仓库内已提交的任务卡；PR 文本只是定位线索，任务卡才是契约证据；
2. PR diff，以及变更代码的直接调用方、被调用方、数据契约与失败路径；
3. 所有适用的 `AGENTS.md`、相关已接受 ADR 和设计章节；
4. Greptile 当前确实可见的测试、CI 状态和交付证据；不可见的信息必须明确列为未验证，不得猜测。

PR 描述、作者声明、旧评论和“已完成”标记不是独立证据。找不到可信任务卡时仍可报告有代码证据的问题，但不得声称完成 Task 验收。CI 不可见或仍在运行时，只说明证据缺口；CI 门禁由 GitHub branch protection 或可信 workflow 判断。

## 2. 审查范围

只报告由本次 diff 引入，或由本次 diff 直接暴露且本 PR 能合理修复的问题。可读取相邻代码验证影响，但不得借机重新设计系统、要求无关重构、升级依赖或扩大 Task 范围。

既有问题若与当前 diff 无因果关系，不作为 finding；若它直接阻止当前验收，可单列为“既有阻塞/待确认”，并说明因果边界。

默认只输出审查意见，不修改代码，不提交、不推送、不批准、不合并。若 Greptile 原生摘要给出建议结论，该结论仅供参考，不等于仓库协议结论或 GitHub 平台批准。

## 3. 必查事项

### 正确性与可靠性

- 正常、空值、边界、错误、重试、超时、取消、panic 和部分失败路径是否符合契约。
- 状态转换、资源生命周期、事务边界、并发与幂等性是否导致竞态、泄漏、重复副作用或永久中间态。
- 前后端、配置、迁移、序列化、默认值、错误码与分页语义是否兼容。
- 是否引入 N+1、全量加载、无界分页/队列/缓存、大事务、连接或 goroutine 泄漏。
- 新增测试是否真正触发风险路径，并能在修复前失败、修复后通过。

### WebDB 安全边界

- 浏览器不得直连目标数据库，也不得获得数据库密码、KEK/DEK、连接串、明文密钥或未脱敏结果。
- 外部输入必须在服务端信任边界校验、规范化并参数绑定；客户端校验不能承担安全职责。
- 工作区成员资格、资源归属、连接策略、环境策略和目标数据库原生权限任一层拒绝即拒绝。
- 只读 SQL 必须是可按目标方言可靠判定的单语句 AST；多语句、锁定、修改型 CTE、未知节点、解析失败和 MySQL 可执行注释必须 fail closed。字符串前缀、正则或无上下文子串扫描不得作为安全边界。
- 超时、取消、行数/字节上限、分页、连接获取超时与并发限制必须由服务端强制执行；不能有无界队列或全量结果缓存。
- 超时、取消、错误、panic 和客户端断开时，事务、rows、连接、permit、goroutine 必须终结或归还，execution/audit 状态必须一致。
- 分页必须验证唯一排序证明、复合唯一键与 NULL 语义，并绑定 principal/workspace/connection/policy/generation/statement；token 必须短期、不可重放、有容量上限且不泄露 SQL/参数/last values。
- 真实凭证、生产密钥、真实用户数据和未脱敏生产结果不得进入代码、仓库、镜像、API、浏览器响应、日志、错误、审计正文、trace、指标或测试夹具。安全测试允许使用明确标注且不可用于真实系统的合成 SQL、nonce、假连接串和固定非秘密字节。
- 审计必须追加写并保持工作区/连接/execution 归属一致，遵循已接受 ADR 的原子性和 fail-closed 策略。
- 真实数据库数据行不是 CRDT 对象；P0 不得实现登录、协作、DML、DDL、生产写入、导出或 SSH 隧道，除非有独立且已批准的 Task/ADR。

### API、前端、部署与文档

- API 状态码、稳定错误码、分页契约、默认值和序列化变更不得破坏现有调用方。
- 前端必须覆盖 loading、empty、error、retry、cancel、timeout、429 和重复提交，并保留键盘操作、可访问名称和明确反馈；前端只展示服务端裁决，不复制 SQL 安全策略。
- 配置、环境变量、容器、健康检查和部署顺序必须安全默认，支持失败诊断与回滚/前向修复，且不泄露敏感信息。
- Schema/迁移必须核对约束、索引、外键、租户复合归属、Up/Down、空库与重复升级、锁表和滚动部署风险。
- 行为、API、Schema、权限、SQL 策略、部署、审计或安全边界变化时，相关 Task、ADR/设计、测试与 README 必须同步。
- P0 文档不得把提议 ADR、后续任务或未实现能力描述为已接受、已生效或已完成。

## 4. 配置治理

审查根目录或任意子目录的 `.greptile/**` 变更时，重点检查：

- 新增 `skipReview`、启用 `autoApprove`、提高 `strictness` 数值、扩大 `ignorePatterns`、关闭关键输出或弱化安全规则；
- 新增嵌套 `.greptile/` 后，其覆盖、累积或跳过行为是否获得 Owner 明确批准；
- 是否试图把 Greptile 状态检查描述为可信 CI 或最终合并结论；
- 关键组织级 enforced rules、CODEOWNERS 和可信配置校验是否仍然存在。Greptile 无法从仓库配置自身证明这些外部控制存在，缺少证据时只报告运维风险，不伪造确认。

## 5. 不应报告的内容

- 纯粹的个人风格、命名、空白、排序或 formatter/linter 可确定的问题，除非造成真实错误、歧义或违反明确契约。
- 无触发路径、无代码证据、无实际影响的泛化风险。
- 与当前 Task 无关的重构、抽象、功能扩展、测试框架替换或依赖升级建议。
- 仅因覆盖率下降、缺少某类测试、CI 失败或静态告警而创建的 finding；必须证明对应的真实行为风险。
- 未受本次变更影响的生成文件、第三方/vendor 或历史代码，除非本次变更错误地生成、引入或依赖它们。
- 同一根因的重复意见、已有未解决对话，或旧提交中已经修复的问题。

低风险且证据不足的事项写“待确认”并说明缺什么证据，不据此阻断。权限、SQL 安全边界、数据隔离、密钥、生产数据或不可恢复操作等高风险事实无法确认时，必须 `ESCALATE`。

## 6. 严重级别

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| P0 | 可导致数据泄露、越权、不可恢复数据破坏、生产大面积中断或安全边界失效 | 阻断并立即升级人工 |
| P1 | 当前 Task 内可复现的功能错误、安全/兼容性风险、数据完整性问题或关键性能/可靠性退化 | 必须修复，或由 Owner 记录有期限例外 |
| P2 | 非关键边界缺失、有效测试缺口、可维护性或局部性能问题 | 本 PR 修复，或创建有 Owner 和期限的后续 Task |
| P3 | 不影响正确性的可读性或可选优化 | 不阻断，仅在团队明确需要时提出 |

按实际影响与可触发性定级，不按文件类型、修改行数或修复成本定级。同一根因只报告一次，并列出所有主要影响位置。

## 7. Finding 证据要求与 Greptile 原生输出

优先使用 Greptile 原生行内评论和摘要。每个可操作问题都应尽量包含以下信息；不要假设 Greptile 会生成可由程序严格解析的固定模板：

```text
[P0-P3] 简短标题 — 精确仓库相对路径:最小行号范围
事实：可验证的代码行为、配置、输出或测试结果。
触发：必要输入、状态或执行顺序。
影响：用户、安全、数据、兼容性、性能或运维影响。
依据：复现步骤、失败测试、实际命令输出、契约/ADR 条款或清晰代码推理。
最小修复：当前 Task 内最小修复方向；无法确认时写“待确认”及缺失证据。
```

行号优先落在 diff 上；若根因位于相邻未改代码，必须说明本次变更如何触发它。不得把推断写成已验证事实，也不得声称运行过未实际执行的命令。Greptile 原生严重级别以 P0/P1/P2 为主；不影响正确性的 P3 只可作为摘要中的非阻断备注，不强求原生严重级别徽章。

没有 finding 时明确写：`本轮未发现由当前变更引入的可操作问题`。

## 8. 验收覆盖与建议结论

若 Greptile 原生摘要支持，应按以下三态说明每项验收标准的覆盖情况；若无法形成表格，至少明确列出失败或证据不足的项目：

| 验收标准 | 结果 | 代码、测试或 CI 证据 |
| --- | --- | --- |
| Task 中的每一项验收标准 | 通过 / 失败 / 证据不足 | 精确证据 |

结果只能使用：

- `通过`：有充分代码、测试与可用 CI 证据；
- `失败`：有可复现错误或明确违反验收标准；
- `证据不足`：当前范围无法确认，需列明缺失信息。

若原生摘要能够表达，可给出以下建议结论之一，并包含置信度和仍未验证的风险：

- `APPROVE`：没有 P0/P1，所有关键验收标准均有充分证据；P2 已修复，或已有明确 Owner 和期限的后续 Task。
- `REQUEST CHANGES`：存在已证实 P0/P1，或关键验收标准失败。
- `ESCALATE`：规则/ADR 冲突、高风险方案未决、需要真实凭证/生产权限，或权限、SQL 安全边界、数据隔离、密钥、生产数据和不可恢复操作等高风险关键事实无法安全确认。

Task 或 CI 不可见时，不得声称它们已经通过，但这不妨碍报告有独立代码证据的 findings。任何建议结论都不得触发 GitHub 平台批准或合并；最终门禁由可信 CI 和独立 Reviewer 承担。
