# WebDB 计划书评估

> 评估对象：[webdb-design-draft.md](../webdb-design-draft.md) v0.3 及 P0 任务卡（P0-01 ~ P0-06）
> 评估日期：2026-07-24
> 评估范围：计划书完整性、功能丰富度、风险点与改进建议

---

## 一、总体判断

WebDB 计划书在 **P0 安全基础上扎实且克制**，但功能丰富度偏保守，整体定位更像"安全可审计的团队 SQL 终端"而非"团队数据库 IDE"。

这个定位本身是合理的——[设计稿 1.2](../webdb-design-draft.md#L22-L28) 明确放弃"第一阶段支持数十种数据库"和"功能更多取胜"。但它也带来一个值得讨论的张力：**在差异化卖点（受控写入闭环）真正落地之前，产品对用户的吸引力主要靠"协作 + 审计"，这可能不足以支撑 P0-P2 阶段的持续采用。**

---

## 二、计划书的完整性：强

### 2.1 安全与合规维度 —— 业界少见的扎实

| 维度 | 覆盖情况 |
|---|---|
| 凭证管理 | 信封加密（DEK+KEK）、版本化、轮换预留、不入库明文 |
| SQL 安全 | 方言 AST 双解析器、fail-closed、单语句、可执行注释识别 |
| 审计 | 追加写不可变、DB 层拒绝 UPDATE/DELETE、脱敏白名单 |
| 权限 | 四层交集（RBAC + 连接策略 + 环境策略 + DB 原生权限） |
| 隔离 | 双网络隔离、端口仅 `127.0.0.1`、API 唯一可达 DB |
| 威胁建模 | 8 类风险 + 控制措施 + 验证方式（[设计稿 8.1](../webdb-design-draft.md#L280-L292)） |
| SLO | 6 项可测量指标（[设计稿 8.2](../webdb-design-draft.md#L293-L304)） |

这套设计在同类自托管产品里属于**第一梯队**。CloudBeaver / Outerbase 在团队权限上做得不错，但 WebDB 把"信封加密 + 方言 AST + 审计不可变 + fail-closed"做到 ADR 级别，是真正的差异化。

### 2.2 工程治理 —— 严谨

- 13 个 ADR 锁定关键决策
- 任务卡 → Ready → Done 流程
- 独立审查（Codex）+ 多轮 CodeRabbit
- 依赖 Spike 前不批准依赖
- P0/P1/P2/P3/P4 分期清晰，每期有"明确不做"

### 2.3 文档体系 —— 完整

设计稿、ADR、任务卡、AGENTS.md 协作规则、模板（ADR / PR / 任务卡 / Prompt）齐全，权威来源优先级链明确。

## 三、功能丰富度：偏保守

### 3.1 与主流数据库 GUI 的功能差距

| 能力 | DBeaver / DataGrip | WebDB v1（P0-P2） | 评价 |
|---|---|---|---|
| 多数据库支持 | 80+ | **仅 PG/MySQL** | 范围克制，但团队若有 SQLite/SQL Server/Oracle 就用不了 |
| ER 图 / 可视化 | ✅ | P4 才做 | 落后较多 |
| Schema diff | ✅ | P4 才做 | 落后较多 |
| 数据生成 / 迁移 | ✅ | **不做**（非目标） | 明确放弃 |
| 查询计划可视化 | ✅ | 仅 EXPLAIN 文本 | 弱 |
| AI 辅助 SQL | 部分有 | P4 才做 | 落后 |
| 图形化数据编辑 | ✅ | P3 才做受控变更 | 落后 |
| SSH 隧道 | ✅ | P4 才评估 | 落后较多 |
| 离线编辑 / 同步 | ❌ | CRDT 协作 | **WebDB 优势** |
| 共享查询 + 审计 | 弱 | **核心** | **WebDB 优势** |

### 3.2 P0-P2 阶段功能可能不够"打动用户"

P0 + P1 + P2 完成后，用户拿到的是：

- 能登录、能连 PG/MySQL、能写 SQL、能看结果、能 CSV 导出
- 能多人协作编辑 SQL 文本、有审计

**但还缺**：

- 没有数据行编辑（P3 才做）
- 没有 ER 图、Schema diff（P4）
- 没有 SSH 隧道（P4 才评估，私网外团队用不了）
- 没有 AI 辅助
- 只支持两种数据库

**风险**：在 P2 结束前，对**单人用户**而言，WebDB 相比 DBeaver / TablePlus 几乎没有功能优势，唯一的卖点是"团队协作 + 审计"。如果首发团队没有强协作诉求，可能用不下去。

### 3.3 计划书自身的诚实

设计稿在 [2.3 竞品调研](../webdb-design-draft.md#L52-L54) 主动承认："WebDB 不能仅以'功能更多'取胜"，并定位差异化为"开源自托管环境中的实时共享工作上下文、受控执行与可审计变更闭环"。这是清醒的判断。

## 四、值得讨论的张力点

### 4.1 "先 SQL 后图形" vs 用户期待

[设计稿 3.1](../webdb-design-draft.md#L69-L74) 范围原则说"可视化 Schema 设计器是后续增值功能，不阻塞核心工作流"。

这对 DBA / 数据分析师友好，但对**产品经理、运营、数据分析师**这类非 SQL 熟手用户不友好。

**建议**：在 P1 / P2 之间增加一个**图形化数据浏览**（表格视图 + 筛选排序 + 行详情）的轻量任务，否则非技术用户用不起来。

### 4.2 协作功能的真实价值待验证

[设计稿 2.2](../webdb-design-draft.md#L43-L50) 列了 4 个待验证假设，其中"团队愿意把排查 SQL 沉淀为共享资产"是核心。

**但 P0-P2 整个路线图里没有看到验证这个假设的具体计划**——没有用户访谈安排、没有 POC 试用团队、没有验证信号收集机制。

**建议**：在 P0 验收后、P1 启动前补一个**用户验证任务卡**，落实 4 个假设的验证，再决定 P1 范围。否则可能花 4-6 周做完 P1 才发现假设不成立。

### 4.3 P3"受控变更"可能是真正的差异化卖点，但被推得太后

P3 的 DML 预览 + 影响行数 + 二次确认 + 审批 + 审计导出，这套"受控写入闭环"才是 WebDB 区别于所有 GUI 的**真正杀手锏**——CloudBeaver 有数据编辑但没有审批闭环。

但它被排在 P3（第 10-16 周），很多团队可能等不到。

**建议**：考虑把 P3 的"DML 预览 + 影响行数 + 二次确认"（不含审批）提前到 P1 或 P2，审批闭环留 P3。让团队更早体验到"安全地改一行数据"。

### 4.4 SSH 隧道后置限制采用

P4 才评估 SSH / 跳板机连接（ADR-009）。对**私网外的团队**（云上数据库 + 远程办公）而言，没有 SSH 隧道意味着根本连不上目标库。

**建议**：SSH 隧道值得提前评估，至少在 P2 前完成拓扑设计，否则会大幅限制采用场景。

## 五、缺失的关键工程项

| 缺失项 | 影响 | 建议补充位置 |
|---|---|---|
| **备份 / 恢复** | SLO 提了"每日备份"但无任务卡 | P1 启动前补任务卡 |
| **监控 / 告警** | SLO 提了指标但无可观测性任务 | P1 期间 |
| **多租户隔离测试** | 安全设计有，但没有专门的渗透测试任务 | P2 收尾或 P3 启动前 |
| **端到端压测** | P0-03-followup 有连接池压测，但缺端到端压测 | P0 验收阶段 |
| **国际化预留** | 明确 v1 不做，但代码层 i18n 预留也没提 | P1 设计阶段（即使不做也应预留） |

## 六、评分总结

### 6.1 分维度评分

| 维度 | 评分 | 说明 |
|---|---|---|
| 安全 / 合规 | 9 / 10 | 业界领先 |
| 工程治理 | 9 / 10 | ADR + 任务卡 + 审查流程严谨 |
| 数据模型 | 8 / 10 | P0 8 表完整，后续实体预留 |
| 架构清晰度 | 9 / 10 | 分层、边界、决策理由都清楚 |
| 功能丰富度 | **6 / 10** | P0-P2 偏保守，差异化靠 P3 / P4 |
| 用户验证 | **5 / 10** | 假设有但无验证计划 |
| 运维 / 可观测 | 6 / 10 | SLO 有但缺落地任务 |

### 6.2 总体结论

- **作为安全可审计的团队数据库工作台**，计划书完整度 **8.5 / 10**
- **作为通用数据库 IDE**，功能丰富度 **6 / 10**

## 七、改进建议（按优先级）

### P0 收尾阶段

1. **补端到端压测任务卡**：在 P0 验收脚本中覆盖完整链路压测
2. **P0 验收威胁模型**：落实 [设计稿第 374 行](../webdb-design-draft.md#L374) 的"威胁模型"产出

### P1 启动前

3. **补用户验证任务卡**：落实 [设计稿 2.2](../webdb-design-draft.md#L43-L50) 的 4 个假设验证（3 个真实团队访谈 + 试用），再决定 P1 范围
4. **补备份 / 恢复任务卡**：落实 SLO 的"每日备份 + 季度恢复演练"
5. **补可观测性任务卡**：把 SLO 落地为监控告警

### P1 / P2 期间

6. **把 P3 的 DML 预览前移**：把"DML 预览 + 影响行数 + 二次确认"（不含审批）提前到 P1 或 P2，让团队更早体验差异化卖点
7. **补图形化数据浏览任务**：降低非 SQL 用户的门槛
8. **SSH 隧道提前评估**：至少在 P2 前完成拓扑设计（ADR-009 推进）

### P2 收尾或 P3 启动前

9. **补多租户隔离渗透测试任务卡**：专项验证跨工作区 / 跨连接 / 越权 ID 防护
10. **i18n 预留**：即使 v1 不做国际化，P1 设计阶段也应预留代码层接口

---

## 八、一句话总结

> 计划书在"做对的事"上无可挑剔，但在"做够多的事"上偏保守。
> 差异化卖点（受控写入闭环）被推到 P3 是最大的风险——
> 建议把它的前置部分提前，让团队更早感受到 WebDB 的独特价值。
