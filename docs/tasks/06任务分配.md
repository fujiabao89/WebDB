这里的“并发 A/B/C/D”默认指四条独立工作流，不是每条再拆成很多 Agent。最稳妥的配置是：一个 Linear Task、一个实现 Agent、一个分支和一个 PR；完成后再由其他 Agent 独立审查。

## 推荐分配

如果有 4 个并发执行槽：

| 角色 | Linear Task | 负责内容 |
| --- | --- | --- |
| 主 Agent / Agent A | WEB-35 并发 A | HTTP、结果 DTO、执行、取消、审计确认 |
| Agent B | WEB-38 并发 B | SchemaSnapshot、VerifiedSortPlan、continuation registry |
| Agent C | WEB-36 并发 C | 授权连接列表、Schema 浏览 API |
| Agent D | WEB-37 并发 D | 高保真前端生产化与 API 接入 |

主 Agent 同时承担跨任务协调，但不能替其他 Agent直接修改其负责范围。

开始顺序：

1. WEB-34 Owner Gate 已由 Owner 接受（2026-08-13，见 `P0-06A-http-contract-owner-gate.md`），作为 A/B/C/D 的实施基线，无需再等待批准。
2. A/B/C/D 四个 Agent 基于该已接受基线同时启动。
3. 四项完成后，另安排集成 Agent执行 WEB-39。
4. PR Ready 后交叉独立审查，不能由实现者批准自己的 PR。

## 并发 A 怎么做

WEB-35 建议只交给一个实现 Agent，因为 HTTP handler、错误映射、Execution 生命周期、取消和审计失败策略耦合紧密，多人同时修改很容易产生不一致。

Agent A 内部按以下顺序推进：

### A1：HTTP 边界

- `/api/v1` 路由和依赖注入
- 可信 Principal
- JSON 请求限制
- 统一成功/错误 envelope
- HTTP 状态与稳定错误码
- 429 `Retry-After`
- `/health` 兼容

### A2：结果传输 DTO

依赖 WEB-10：

- 数据库类型转公共 `wire_type`
- NULL、decimal/int64、时间、JSON、二进制编码
- 单元格、行数、页面和响应字节限制
- 禁止序列化驱动私有类型

### A3：执行和分页 HTTP

等待 Agent B 交付内部接口：

- 首页只读执行 handler
- next-page handler
- 客户端不能提交 engine、actor、policy 上限或 `unique`
- `query_timeout`、`query_cancelled` 等公共错误归一
- Adapter 错误的完整脱敏映射

### A4：取消和审计

- request context 取消传播
- 连接和 permit 归还
- Execution 状态转换
- 首页/续页审计
- audit receipt
- 审计失败扣留结果
- 安全告警

### A5：测试与交付

- handler 契约测试
- 策略拒绝时目标库零调用
- 取消、超时、panic、客户端断开
- 审计故障注入
- 敏感 canary
- 验收矩阵和交接证据

也就是说，A1～A5 是一个 Agent 在一个分支内的小任务，不是五个 Agent同时写代码。

## 并发 B 怎么做

Agent B 独占分页安全相关代码：

1. PostgreSQL/MySQL 唯一约束元数据。
2. SchemaSnapshot。
3. sealed `VerifiedSortPlan`。
4. Adapter 接口迁移。
5. Service-owned registry。
6. token claim/rotate/abort。
7. NextPage 重新授权。
8. 并发、过期、重放、撤权和 fuzz 测试。

Agent B 先向 Agent A 交付接口签名，Agent A 可基于 fake/mock 开发 HTTP handler；Agent B 不修改 HTTP 层。

## 并发 C 怎么做

Agent C 负责授权浏览链路：

1. 共享的只读授权服务。
2. 安全连接 DTO。
3. 授权连接列表。
4. schemas/tables/columns 懒加载。
5. 参数绑定和标识符校验。
6. 凭证解析顺序。
7. 跨工作区不可枚举测试。
8. 双引擎 Schema 集成测试。

Agent C 不修改分页证明，也不修改执行 handler。

## 并发 D 怎么做

Agent D 负责高保真页面生产化：

1. 盘点现有页面和依赖。
2. 提取设计 token、组件和 P0 范围映射。
3. 类型化 API client 与 mock。
4. 连接列表和 Schema 树。
5. Monaco、结果表和下一页。
6. 取消、429、超时、审计失败等状态。
7. 可访问性。
8. 视觉回归和浏览器测试。

Agent D 先使用 WEB-34 冻结的 mock 契约，不等待后端完成；A/C 交付真实 API 后再替换 mock。

## 是否可以在一个并发内使用多个 Agent

可以，但建议只用于两类工作：

- 一个实现 Agent写代码，另一个 Agent只读检查契约和测试覆盖。
- 两个 Agent修改完全隔离的包，并由一个 Lead Agent统一集成。

例如并发 A 若确实需要加速，可以这样分：

| Agent | 范围 | 是否写代码 |
| --- | --- | --- |
| A-Lead | HTTP、执行管线、最终集成 | 是 |
| A-DTO | 独立结果转换包及单元测试 | 是 |
| A-Security | 错误码、敏感信息、取消/审计测试审查 | 先只读，缺口确认后再提交给 Lead |

但不建议 A-Lead 和另一个 Agent同时修改 handler、execution pipeline 或路由装配。共享文件并行写入的冲突成本通常高于收益。

## 独立审查分配

四个实现 Agent完成后可以交叉审查：

- Agent B 审查 WEB-35。
- Agent C 审查 WEB-38。
- Agent D 审查 WEB-36。
- 另一个未实现 WEB-37 的 Agent审查前端。
- WEB-39 最终验收由没有实现主要链路的 Agent主导。

这样既保持真正并行，也符合“实现 Agent不能担任自己 PR 的最终独立 Reviewer”。
