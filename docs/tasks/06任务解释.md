这套拆分的核心逻辑是：先冻结安全契约，再让后端基础、分页安全、授权浏览和前端四条线路并行，最后统一集成验收。它目前是实施提案，不代表 Owner Gate 已批准，也不代表 API 已定案。

## WEB-34／P0-06A：HTTP 契约与 Owner Gate

**有什么用**

统一决定路由、请求/响应 DTO、错误码、身份来源、分页语义、取消方式、审计模型和各类资源上限。

**解决什么问题**

避免不同开发者分别实现接口时，对同一个概念做出互不兼容的解释。例如：

- 一页查询算一次执行，还是全部页面算一次执行？
- 取消只依赖断开 HTTP，还是提供显式取消接口？
- 审计失败时能否返回查询结果？
- 浏览器身份从哪里来，哪些 header 可以信任？
- Schema 浏览是否进入审计？

**没有它会怎样**

最危险的不是返工，而是安全边界在实现过程中被“顺手决定”。前后端可能形成不同契约，分页和审计也可能出现无法补救的数据模型冲突。

**为什么现在这样安排**

这些问题会同时影响所有后续任务，而且其中不少属于新增 API、身份、权限和审计策略，按仓库规则必须经过 Owner Gate。

**缺点**

- 所有实施任务都会被它阻塞。
- Owner 决策慢时，开发启动也会变慢。
- 过早冻结过多细节可能降低后续调整空间。

所以这里只冻结安全关键和跨模块字段，不应把内部实现细节全部写死。

---

## WEB-35／P0-06B：HTTP 基础、结果 DTO、执行、取消与审计

**有什么用**

把已有的只读查询能力安全地暴露为 HTTP API，包括：

- HTTP 基础设施和统一错误 envelope。
- 可信 Principal 注入。
- 查询结果到 JSON 的稳定转换。
- 首页查询与续页执行。
- 请求取消。
- 审计持久化确认。

**解决什么问题**

Go 数据库驱动类型不能直接稳定地交给浏览器。错误、超时、取消和审计失败也需要形成统一的外部行为。

例如 `int64` 和 decimal 如果直接作为 JSON number，可能在 JavaScript 中丢失精度；数据库错误如果直接返回，则可能泄漏 SQL、主机或驱动内部信息。

**没有它会怎样**

前端只能使用 Mock，无法真正执行查询；或者不得不直接依赖内部 Go 类型和不稳定错误文本，造成兼容性、安全性与精度问题。

**为什么采用这种实现**

选择“薄 HTTP 层 + 独立 wire DTO + 复用既有执行策略”的方式，因为：

- SQL 安全判断仍由服务端既有策略负责。
- HTTP 层不重复实现 SQL 解析。
- 公共 DTO 隔离数据库驱动和浏览器。
- 只有审计成功持久化后才返回 receipt 和结果。
- 请求 context 是最小、最可靠的第一层取消机制。

**缺点**

- 它是最大的集成任务，容易形成共享代码热点。
- 同时依赖 WEB-10 的类型规范化和 WEB-38 的分页接口。
- 如果加入显式取消，必须维护有界执行 registry，会增加并发状态和清理复杂度。
- 审计失败时扣留结果会降低可用性，但这是更安全的失败策略。

---

## WEB-38／P0-06C：SchemaSnapshot、VerifiedSortPlan 与 Service-owned 分页

**有什么用**

证明查询具有可重复、唯一且可信的排序，然后由服务端生成、保存、消费和旋转 continuation token。

**解决什么问题**

单向分页不能只依赖客户端传来的排序字段或 `unique=true`。如果排序不唯一，翻页期间可能出现：

- 重复行。
- 遗漏行。
- 顺序漂移。
- 跨查询或跨连接重放 token。
- 撤权后继续取数。

该任务通过目标库元数据验证主键或完整非空唯一约束，并把可信结论封装成 `VerifiedSortPlan`。

**没有它会怎样**

分页只能退化为不稳定的 offset 分页，或者信任客户端声明。前者在数据变化时会漂移，后者直接破坏安全边界。

**为什么采用这种实现**

选择 service-owned continuation registry，而不是让客户端持有全部分页状态，因为服务端需要：

- 重新检查成员资格和策略。
- 绑定 workspace、connection、execution 和 schema generation。
- 原子消费 token，防止并发重放。
- 设置 TTL、容量和配额。
- 在服务重启、策略变化或撤权后使 token 失效。

**缺点**

- token 带有服务端状态，不是完全无状态的 API。
- 服务重启会使现有 token 失效。
- registry 需要容量、TTL、原子旋转和并发测试。
- 仅支持能够证明唯一排序的查询；join、聚合及复杂查询可能无法分页。
- PostgreSQL 和 MySQL 的元数据差异会提高实现成本。

这是有意选择的“安全优先、能力较窄”方案。

## WEB-36／P0-06D：授权连接列表与 Schema 浏览

**有什么用**

让用户只能看到自己当前有权读取的连接，并按需浏览 Schema、表和列。

**解决什么问题**

数据库连接内部包含 host、凭证引用、密钥版本等敏感字段，不能直接序列化现有 Go model。Schema 浏览也不能因为用户知道 connection ID 就允许访问。

**没有它会怎样**

前端无法选择连接或浏览数据库结构；如果直接复用内部对象，还可能泄漏连接信息，或产生跨工作区对象枚举漏洞。

**为什么采用这种实现**

选择：

- 专用公开 DTO，而不是直接返回持久化 model。
- 先授权，再解析凭证、访问目标数据库。
- schemas、tables、columns 分层懒加载。
- 每一级请求都重新检查授权。
- 标识符按 Adapter 支持的安全方式处理。
- 继续尊重目标数据库原生权限。

懒加载可以避免一次读取完整 catalog，也符合高保真 Schema 树的交互方式。

**缺点**

- 展开 Schema 树会产生多次网络和数据库请求。
- 每级重新授权有额外开销。
- 不做缓存时，大型数据库浏览速度可能一般。
- P0 没有逐 Schema ACL，只能依赖连接级策略和目标数据库权限。
- PostgreSQL/MySQL 的系统 Schema 展示规则可能不完全一致。

---

## WEB-37／P0-06E：高保真工作台生产化与 API 接入

**有什么用**

把已有高保真页面转化为能够连接真实 API、处理真实状态并满足可访问性要求的 P0 工作台。

**解决什么问题**

高保真页面通常证明了布局和视觉方向，但不一定覆盖：

- 加载、空数据和失败。
- 429、超时和策略拒绝。
- 请求取消与迟到响应。
- token 失效。
- 审计失败。
- 键盘操作和可访问名称。
- API 类型变化。
- 重复点击和竞态。

**没有它会怎样**

后端 API 即使完成，用户也无法通过完整界面使用；或者页面只在理想 Mock 数据下工作，遇到真实错误就显示错误状态、旧结果或重复提交。

**为什么采用这种实现**

保留高保真页面作为视觉基线，只做生产化和 P0 收敛：

- 建立类型化 API client。
- 将 Mock 和真实 API 使用同一契约。
- 接入连接、Schema、执行、取消、分页和审计状态。
- 隐藏或禁用登录、协作、保存、导出、历史、编辑和写操作等非 P0 功能。
- 增加可访问性与视觉回归检查。

**缺点**

- 视觉稿和实际 API 契约可能不完全匹配，需要局部调整。
- 为错误状态和可访问性增加的 UI 会提高组件复杂度。
- 非 P0 按钮被隐藏后，页面可能与原始设计稿存在视觉差异。
- 如果后端契约较晚变化，前端会产生一定返工。

## WEB-39／P0-06F：Compose E2E、安全回归与交接

**有什么用**

把前面四条并发线路汇合起来，在真实 Compose 环境中验证完整流程和关键失败路径。

**解决什么问题**

单元测试和模块测试无法证明整体系统正确。例如：

- 前端字段名与后端 DTO 不一致。
- PostgreSQL 正常但 MySQL 失败。
- 取消后数据库连接没有归还。
- 审计失败时后端扣留了结果，但前端仍显示旧结果。
- 撤权后已有 token 还能使用。
- API 已脱敏，但代理或 UI 又暴露内部错误。

**没有它会怎样**

每个 PR 都可能单独通过，但实际演示流程仍无法工作。安全问题也可能只在模块连接后出现。

**为什么采用这种实现**

将 E2E 放在最后统一执行，因为它需要完整的连接、Schema、执行、分页和 UI。覆盖 PostgreSQL/MySQL 主流程，以及越权、超时、取消、重放、审计失败等关键场景。

**缺点**

- 反馈时间比单元测试晚。
- Compose E2E 相对慢，也更容易受环境影响。
- 如果前置任务的接口偏差太大，问题会集中在最后暴露。
- 它适合验证集成，不能代替各任务自己的精细测试。

## WEB-10：查询结果类型规范化前置任务

**有什么用**

先在内部统一不同数据库驱动返回的值类型，再由 WEB-35 转换成公共 HTTP DTO。

**解决什么问题**

PostgreSQL 和 MySQL 对整数、decimal、时间、JSON、二进制等类型的返回形式不完全一致。直接在 HTTP handler 中处理会把驱动差异扩散到整个 API。

**没有它会怎样**

同一列在不同数据库或驱动版本下可能产生不同 JSON，甚至发生数值精度丢失、二进制误解码或不可序列化错误。

**为什么单独作为前置任务**

内部类型规范化和外部 wire DTO 是两个边界：

```text
数据库驱动值
    ↓ WEB-10
稳定的内部结果类型
    ↓ WEB-35
稳定的 HTTP JSON DTO
```

这样 Adapter、Service 和 HTTP 层职责更清楚，也更容易独立测试。

**缺点**

- 多了一层转换和类型定义。
- WEB-35 必须等待其关键语义稳定。
- 如果内部类型设计得过度通用，可能增加维护成本。

---

总体权衡可以概括为：

| 选择 | 得到的好处 | 付出的代价 |
|---|---|---|
| Owner Gate 先行 | 防止安全契约被实现者擅自决定 | 实施启动较慢 |
| 专用 HTTP DTO | 稳定、脱敏、跨驱动 | 增加转换代码 |
| VerifiedSortPlan | 分页顺序可信 | 支持的 SQL 形状较窄 |
| Service-owned token | 可撤权、防重放、可配额 | 有状态，重启后失效 |
| 每级重新授权 | 防止越权和陈旧授权 | 请求成本增加 |
| 审计成功后返回结果 | 审计与结果一致 | 审计故障影响查询可用性 |
| 高保真稿生产化 | 保留设计投入 | 必须补齐大量非理想状态 |
| 最终 E2E 汇合 | 验证真实整体行为 | 问题发现时间相对靠后 |

因此，这套方案不是追求最少代码，而是优先确保：浏览器不获得敏感信息、客户端不能声明安全事实、撤权能够及时生效、分页不能被重放、审计与结果保持一致。
